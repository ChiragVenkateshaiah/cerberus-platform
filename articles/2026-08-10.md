# Week of 2026-07-30–2026-08-10: Phase 1 complete — a working, queryable lakehouse, built and verified

Phase 0 was foundation work, done by hand on purpose: a repo scaffold, AWS
account hygiene, a manually created S3 bronze bucket, a bash script on a
systemd timer, and a hand-built Terraform state backend nothing had used
yet. The point of Phase 0 was never to be elegant — it was to understand
each piece before automating it. Phase 1's job was to turn that hand-built
foundation into an actual, working lakehouse, provisioned entirely as code:
synthetic payments landing in bronze, promoted through silver to a curated
gold layer, and queryable in Athena — with `terraform apply` building the
whole thing and `terraform destroy` tearing it down cleanly. As of today,
that's done. Not "should work" — actually run, live, and verified.

## The shape of the work

Every non-trivial decision in Phase 1 started as an ADR before any code got
written. ADR 0002 settled the medallion layout: three buckets (bronze,
silver, gold), daily `dt=YYYY-MM-DD` partitions, raw JSON in bronze
converting to Parquet+Snappy from silver onward, and bronze staying
immutable and append-only. ADR 0003 settled the data model on top of that
container: a single denormalized "payment event" per lifecycle step
(`created` → `authorized` → `settled`/`failed`, plus refunds), never a
mutated status field — append-only, so the pipeline can always be rebuilt
by reprocessing bronze from scratch.

That reprocessing property turned out to matter more than it looked on
paper. `transform/scripts/promote_payments.py` does a **full rebuild every
run** rather than tracking a watermark — the simplest correct option at
this data volume, and trivially idempotent. It writes silver as the
complete flattened event history and resolves gold's current-state table
via latest-event-wins per `transaction_id`, running as a scoped
`cerberus-transform` IAM role rather than an admin identity. Three
Terraform-managed S3 buckets back all of it (`hashicorp/aws` provider),
with bronze specifically **adopted** via `terraform import` rather than
recreated, since it already held real ingested data by the time Terraform
entered the picture.

IAM was where least-privilege stopped being a slogan and became something
verified by hand. Each of the three roles — ingestion, transform, serving
— gets exactly the permissions its job needs, nothing borrowed from a
shared "admin-lite" policy:

```hcl
resource "aws_iam_role_policy" "ingestion" {
  name = "cerberus-ingestion-policy"
  role = aws_iam_role.ingestion.id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Sid      = "WritePaymentsToBronze"
        Effect   = "Allow"
        Action   = "s3:PutObject"
        Resource = "${var.bucket_arns["bronze"]}/payments/*"
      }
    ]
  })
}
```

That's the entire ingestion role's permission surface: `PutObject`, one
prefix, nothing else — no `ListBucket`, no read access, no reach into
silver or gold. The `hashicorp/aws` provider's `aws_iam_role_policy`
resource keeps this inline and role-scoped rather than a shared managed
policy, deliberately: nothing here is meant to be reused across roles, so
there's no reuse case a standalone policy would buy. And this wasn't just
declared and trusted — I assumed the role via `sts:AssumeRole` and
confirmed the denials by hand: writes outside `payments/` fail, reads fail
entirely, `ListBucket` fails. Declaring a boundary and testing it are
different levels of confidence, and only one of them counts.

The last real piece of Phase 1's design work was the fact/dimension split
ADR 0003 deliberately deferred out of the transform: gold's
`payments_current` is denormalized on purpose, one row per transaction with
merchant and customer detail embedded inline. dbt is what turns that into
`fct_transactions`, `dim_merchants`, and `dim_customers` — a real star
schema, not a flat table pretending to be one:

```sql
with ranked as (
    select
        *,
        row_number() over (
            partition by transaction_id
            order by event_timestamp desc
        ) as rn
    from {{ source('cerberus_platform', 'payments_events') }}
)

select
    transaction_id, event_type as status, event_timestamp as last_event_at,
    amount, currency, merchant_id, customer_id
from ranked
where rn = 1
```

Same latest-event-wins resolution the Python transform uses for
`payments_current`, expressed here as a SQL window function instead — and
this version emits `merchant_id`/`customer_id` as foreign keys rather than
embedding the merchant's name and category on every row. dbt runs against
Athena, which meant standing up a workgroup and a query-results bucket as
1.9's prerequisite — and immediately hitting a real gotcha. With
`enforce_workgroup_configuration = true`, the first `dbt run` succeeded but
silently wrote every table's data into the wrong bucket: dbt-athena's
`CREATE TABLE` macro omits the `external_location` clause whenever the
workgroup enforces its own output location, to avoid the two configs
conflicting. Turning enforcement off fixed it without losing the cost
guardrail — `bytes_scanned_cutoff_per_query` still applies as a default to
any caller that doesn't override it, only the *ability* to override was
what enforcement would have added.

## Proving it, not just building it

The MVP definition of done was never "the code looks right" — it was a
reviewer running one Athena query against gold and getting a result, and
`terraform apply`/`terraform destroy` actually working, not just planned.
Both got tested for real this week. `serving/scripts/run_demo_query.sh`
joins `fct_transactions` against `dim_merchants` for settled revenue by
merchant, running end to end as the read-only `cerberus-serving` role. And
`terraform destroy` was run live against the whole 31-resource stack —
after backing up bronze (the only genuinely non-reproducible layer) and
emptying every bucket — then rebuilt from nothing with `terraform apply`,
bronze restored, and the transform plus dbt re-run to reconstruct
everything. It surfaced two real gaps along the way: the Athena workgroup
needed `force_destroy` to clear its query-execution history before it
could delete cleanly, and — a genuine, useful accident — the rebuild
exposed that silver and gold had silently gone stale four days earlier,
which the full-rebuild-every-run design corrected on its own the moment it
ran again.

The week closed with the first real AWS Well-Architected Tool review this
project has run — not the pillars-as-design-lens method the ADRs used
while building, but the actual Tool, scored against what's really there.
57 questions, answered honestly: 26 high risk, 19 medium, 7 clean, 5 not
applicable at this stage. Sustainability came back cleanest; operational
excellence and reliability scored hardest, mostly because those pillars
assume an organization and standing compute this solo, serverless-only
project doesn't have yet. ADR 0004 writes it up pillar by pillar, and every
real gap maps to a phase that already owns it rather than becoming a new
backlog — observability to Phase 6, multi-account separation and formal
disaster recovery to Phase 7, anything CI/CD-dependent to Phase 5.

## What's next

Phase 2 starts event-driven ingestion — replacing the systemd timer with
Lambda triggered by S3 events or EventBridge, and retiring the timer once
it does. The open question worth sitting with first: how much of Phase 1's
"prove it, don't just build it" discipline — the live destroy/apply test,
the assumed-role permission verification, the honest Well-Architected pass
— carries forward as a standing practice for every phase after this one,
rather than something that happened once because Phase 1 happened to end
on a milestone.
