## 0. Facts

- `orchestration/exercise.sh` has no flag that fails a run. The repo has no
  fault-injection code.
- A failed run is possible with no cluster. `RunTransform` runs
  `aws eks update-kubeconfig` under `set -e`
  (`orchestration/runner/entrypoint_transform.sh`). With `dev-compute` down
  there is no cluster, so the task fails. It retries once after 30 s, then
  `Catch` goes to `PipelineFailed`
  (`orchestration/state_machine.asl.json.tftpl`).
- `InvokeIngestion` runs first and appends a few rows to bronze. Silver and
  gold are not touched. The next passing run promotes those rows (anti-join,
  ADR 0017).
- UNVERIFIED: how fast the Fargate task fails with no NAT (`dev-compute` holds
  the NAT). It may stop at the image pull. Expect 2 to 10 minutes and a few
  cents.
- `exercise.sh` publishes status itself (`start`, then `end`). A hand-started
  run publishes nothing, so section 2 publishes by hand. With no run record,
  `end` reads Step Functions.
- Past times (2 nodes, `docs/demo-recording.md`): apply 793 s, destroy 732 s
  plus a 60 s flush. The cluster costs about $0.40 an hour.
- Past runs (`docs/scale-metrics.md`): the clean 1M run took 581 s and cost
  $0.29. The 10M run cost $0.10. The 100M run cost $0.37. The 2026-11-08 1M
  rehearsal took 394 s.
- Alert timing (`observability/alerts/README.md`): the first email comes about
  3.5 minutes after the finish sample. `CerberusRunFailed` has `for: 2m`. The
  error-budget alert needs at least 5 runs, so it stays quiet.
- PR #191 merged 2026-11-25 and its CI apply finished green.

## 2. The deliberately failed run (no cluster, cents)

Run from your own terminal. Take the state machine ARN from the
`STATE_MACHINE` line in `exercise.sh`. Do not commit the account number.

```
NAME=failcheck-$(date -u +%Y%m%dT%H%M%SZ)
aws --profile cerberus-admin --region us-east-1 stepfunctions start-execution \
  --state-machine-arn <STATE_MACHINE arn> --name "$NAME" --query startDate --output text
AWS_PROFILE=cerberus-admin uv run -q --no-project --python 3.12 --with boto3==1.43.67 \
  python observability/status/publish.py start --execution "$NAME" --send
```

1. Wait until the execution shows FAILED (console or `describe-execution`).
2. Publish the finish: `make status-publish EXECUTION="$NAME" ARGS=--send`.
   The failed step must read `RunTransform`.
3. Confirm no RUNNING execution and no ECS task is left.

Safety: no cluster, so nothing keeps billing. There is no silver or gold
write. It is reversible: the next passing run clears the alert.

Optional later PR: an `exercise.sh --fail-early` flag, only if a repeatable
failure on a real cluster is wanted.

"4 · Pipeline Status: did the last run pass?". Stop it with `make grafana-down`.

- After the failed run (wait 1 to 2 min): Last run = failed. What broke =
  `RunTransform` (not "Fail state"). Data checks = not run. Run result over

- After the passing run: Last run = passed. What broke is empty. Data checks =
  passed. Events handled about 1M. Time per step shows seconds for every step.

**B. Terminal.** Run `make status` after each run.

- The section "Pipeline status (from Prometheus)" shows "Last run : failed" and
  "What broke : RunTransform". Later it shows "passed" with no "What broke".
- "Newest finished run" shows the matching name. "Time per step" shows
  "not reached" after the failed step.
- The old three sections still print. No UNAVAILABLE line for AMP.
- `make cerberus CMD="--json status"`: `data.pipeline.available` is true.
- The web console `status` uses the same code on the Lambda. Optional: it needs
  a paid console session (about 13 min wake). Skip it unless the Lambda path
  must be proven.

**C. Alert email** (3 to 4 minutes after the failed finish publish).

- Subject `[Cerberus FIRING] CerberusRunFailed failcheck-<stamp>`. The
  `execution` must be the failed run, not an older one. The body has
  `make review RUN=failcheck-<stamp>`.
- No DataQualityErrors, NeverReported or ErrorBudgetBurn email. Any of these is
  a finding.
- After the passing run: a RESOLVED email for `CerberusRunFailed` (about 5 to 8
  min, `group_interval 5m`) and no new FIRING email.
- No email after 10 minutes: check spam, the SNS topic and the rule join. The
  smoke path already works, so suspect the join.

**D. Record.** An agent drafts the result for Phases.md 10.6 and the
"Confirmed" line in ADR 0021. The owner reviews it.

## 5. Lineage check: blocked, build first

- The L1 extractor and the L2 hook do not exist. `exercise.sh` has no lineage
  code. `_object_key` appears only in `lineage/collector/handler.py` and docs.
- The orchestrated task definitions set `OPENLINEAGE_URL`
  (`terraform/modules/orchestration_runner/main.tf`, about L170 and L207).
  Spark and dbt-ol then post over HTTP to a route that is IAM-closed outside
  `pipeline_active`. Their events never reach logs or the bucket. The
  2026-10-15 driver log has 0 `"eventType"` lines.
- ADR 0021 Q3 (accepted): use the console transport, extract from the saved
  driver log and the dbt CloudWatch text, upload as `cerberus-admin`. That needs
  the `OPENLINEAGE_URL` env removed from both task definitions (Terraform, CI
  applies), plus an extractor and an upload step.

Recommendation: close 10.6 for status, dashboard, terminal and alert now. Build
L1 (offline extractor and tests) and L2 (exercise hook, env change, upload) as
their own PRs. Then check lineage on one later exercise.

What to look at once L2 exists:

- `aws s3 ls s3://<lineage-bucket>/events/received_date=<today>/ --recursive`.
  The bucket name is `terraform output lineage_bucket_name` in `dev-standing`.
  UNVERIFIED: that `cerberus-admin` can list and read it.
- The object count is above 0, and `events/malformed/` is empty.
- Spark: START and COMPLETE events for `cerberus-promote-payments`
  (`jq -r '[.eventType,.job.name]|@tsv'`).
- dbt-ol: COMPLETE events for the gold models, with column-level lineage facets.
- Keys follow `_object_key`, and the 6.4d renderer shows them.

## 8. Risks and open questions

Risks:

- The failed run may take longer than expected (no NAT, image pull). The outer
  `TimeoutSeconds` is 4500. If it passes 15 minutes, run
  `aws stepfunctions stop-execution`. The result is ABORTED, and `failed_state`
  for ABORTED was never seen live (plan 2026-11-20, section 8).
- The failed run adds a few bronze rows. They are harmless and the next run
  promotes them. UNVERIFIED: the data-quality ledger check reads by `run_id`,
  so it should not count them.
- The failed run stays in the 90-day history, so the pass rate reads 50% for
  now. The error-budget alert needs 5 runs, so it stays quiet.
- The `start` publish comes seconds after the run begins. The `for: 2m` covers
  that gap.
